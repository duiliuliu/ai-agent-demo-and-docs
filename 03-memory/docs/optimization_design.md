# 03-memory 优化设计：实体画像泛化、长期压缩、短期降噪

## 三个深度优化点的思考与设计

### 1. 用户画像泛化：EntityProfile

#### 1.1 为什么需要泛化？

实际场景中"主体"不只有"用户"：
```
- 用户画像：单个用户的信息
- 项目画像：项目的状态、需求、约束
- 产品画像：产品的特性、价格
- 团队画像：团队的成员、角色、能力
- 场景画像：当前任务场景的上下文
```

强行把"主体"绑定为"用户"会导致：
- 项目/产品等信息无法被结构化记录
- 不同主体的关系难以表达
- 加载时无法针对性筛选

#### 1.2 解决方案：泛化的 EntityProfile

**核心抽象**：所有"画像"本质同构——都是"主体的结构化事实集合"。

```python
class EntityProfile(BaseMemory):
    ENTITY_TYPES = ["user", "project", "product", "team", "scene", "other"]
```

**统一的数据结构**：
| 字段 | 用途 | 示例（user） | 示例（project） |
|------|------|-------------|----------------|
| basic_info | 基本信息 | 姓名、年龄 | 项目名、负责人 |
| attributes | 实体属性 | 性别、城市 | 预算、周期 |
| preferences | 偏好 | 饮食偏好 | 技术栈偏好 |
| relations | 关联关系 | - | 关联的用户 |
| states | 状态 | - | 当前阶段（支持TTL） |
| tags | 标签 | VIP | 高优先级 |

**设计要点**：
- `entity_type` 区分主体，但数据结构统一
- `attributes` 替代原先硬编码的"基本信息"，更通用
- `relations` 表达实体间关系（如"项目A"属于"用户B"）
- `states` 支持 TTL 自动过期（短期状态自动清理）

### 2. 长期记忆压缩与去噪

#### 2.1 为什么需要压缩？

原版"原样存储"的长期记忆存在三个问题：

**问题 1：信息冗余**
```
"用户喜欢川菜"
"用户喜欢吃川菜，偏好辣"  ← 重复
"用户喜欢川菜和湘菜"      ← 重复
```

**问题 2：噪音累积**
```
"用户查询了北京天气"
"用户搜索了北京天气信息"   ← 语义重复
"用户查天气"              ← 信息量低
```

**问题 3：低价值记忆污染**
闲聊、错误输入、临时性任务混入长期记忆
→ 占用存储 + 干扰检索 + 增加 Token 消耗

#### 2.2 解决方案：MemoryCompressor 四种决策

```python
class CompressAction(Enum):
    SKIP = "skip"        # 噪音，不入库
    MERGE = "merge"      # 与已有记忆合并去重
    REPLACE = "replace"  # 覆盖旧记忆（如偏好变更）
    APPEND = "append"    # 追加为新记忆
```

**决策流程**：

```
新记忆进入
  │
  ├─ 1. 噪音检测（正则匹配）
  │    单字回应/纯语气/纯标点/长度<4
  │    → SKIP
  │
  ├─ 2. 覆盖信号检测
  │    "改吃"、"不喜欢"、"改为"等
  │    且与某条已有记忆主题相关
  │    → REPLACE
  │
  ├─ 3. 相似度合并检测
  │    相似度 > 0.6
  │    → MERGE（"X川菜" + "X湘菜" → "X川菜和湘菜"）
  │
  └─ 4. 默认追加
       → APPEND
```

**降噪规则（无需 LLM 的轻量版）**：
```python
NOISE_PATTERNS = [
    r"^[嗯哦啊哈嘿]+$",
    r"^(好的|是的|对|行|可以|ok|yes)$",
    r"^(谢谢|多谢|感谢)$",
    r"^[.。，,！!？?~～]+$",
    r"^.{1,4}$",   # 太短
]
```

**合并规则（基于相似度）**：
```python
def _should_merge(self, new, existing):
    sim = compute_similarity(new, existing)
    return sim >= 0.6  # 相似度超过 60% 则合并
```

**REPLACE 信号词**：
```python
REPLACE_SIGNALS = [
    "改吃", "改用", "改成", "换成", "不喜欢", "不爱",
    "其实", "实际上", "更正", "修正", "改为", "不再是",
    "changed to", "instead of", "no longer", "actually",
]
```

#### 2.3 进阶方向（生产环境）

- **LLM 合并**：用 LLM 总结合并多段相似记忆
- **摘要压缩**：对长记忆做 LLM 摘要后入库
- **重要性评分**：每条记忆打分，低于阈值自动归档/淘汰
- **冲突检测**：双向验证（不是单向覆盖）

### 3. 短期记忆：会话段降噪与滚动

#### 3.1 为什么按时间过期是错的？

**错误示例**：
```
10:00 用户说"我改吃粤菜了"（重要信息）
10:01 闲聊 30 分钟
10:30 触发 TTL 过期
→ 用户的饮食偏好变化被错误丢弃！
```

**核心问题**：
- 重要信息可能混杂在噪音中
- 闲聊可能挤掉重要消息
- 按时间窗口切分不符合对话的语义结构

#### 3.2 解决方案：会话段（SessionSegment）滚动

**核心思想**：把短期记忆建模为"会话段"列表，而非平铺消息流。

**会话段的生命周期**：
```
ACTIVE → CLOSED → PROMOTED
  │        │         │
  │        │         └─ 已提取关键信息到长期记忆
  │        └─ 已结束，等待评估
  └─ 当前正在累积消息
```

**滚动策略**：
```python
def add_message(self, role, content):
    # 1. 加入当前活跃段
    self.current_segment.add(role, content)

    # 2. 检测"段边界信号"
    if self._is_segment_boundary():
        # 3. 评分当前段
        density = self._calculate_density(self.current_segment)
        if density > 0.3:
            # 4. 高密度段保留
            self.segments.append(self.current_segment)
        # 5. 触发"段结束"事件
        # → 触发长期记忆压缩流程
```

**段边界检测**：
- 单段 Token 超限（默认 800）
- 长停顿（默认 5 分钟无新消息）
- 手动调用 `force_finalize()`
- 话题切换信号（进阶）

#### 3.3 降噪评分（信息密度）

```python
def _message_value(self, content):
    # 噪音 → 0 分
    if is_noise(content): return 0.0

    # 偏好/决策类 → 1.5 分（最高）
    if has_preference_signal(content): return 1.5

    # 事实陈述 → 0.8 分
    if has_fact_pattern(content): return 0.8

    # 疑问 → 0.6 分
    if is_question(content): return 0.6

    # 致谢/礼貌 → 0.2 分
    if is_polite(content): return 0.2

    # 默认 → 0.5 分
    return 0.5
```

**段的密度阈值（density_threshold=0.3）**：
- 低于阈值的段直接丢弃
- 避免"全部是噪音的段"占用 Token 配额
- 保证留下来的段都是"有信息价值的"

#### 3.4 短期→长期压缩流程

```
会话段结束
  │
  ├─ 段密度 < 0.3 → 直接丢弃
  │
  └─ 段密度 >= 0.3
       │
       ├─ 提取高价值消息（评分 > 0.8）
       │
       ├─ 通过 MemoryCompressor 决策
       │    → SKIP / MERGE / REPLACE / APPEND
       │
       └─ 写入长期记忆 + 向量索引
            → 段标记为 PROMOTED
```

## 三个优化点的协同关系

```
用户输入
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│              短期记忆（SessionSegment）                    │
│  - 按段滚动（非按时间）                                    │
│  - 自动降噪（信息密度评分）                                │
│  - 低密度段直接丢弃                                        │
└─────────────────────┬────────────────────────────────────┘
                      │ 段结束时
                      ▼
┌──────────────────────────────────────────────────────────┐
│              MemoryCompressor（压缩器）                   │
│  - SKIP  : 噪音不入库                                     │
│  - MERGE : 相似记忆合并去重                                │
│  - REPLACE: 偏好变更覆盖旧记录                            │
│  - APPEND : 真正的新信息追加                              │
└─────────────────────┬────────────────────────────────────┘
                      │
                      ▼
┌──────────────────────────────────────────────────────────┐
│              长期记忆（去重后）                            │
└─────────────────────┬────────────────────────────────────┘
                      │
                      ▼
┌──────────────────────────────────────────────────────────┐
│       实体画像（EntityProfile）                            │
│  - 用户/项目/产品/团队/场景 统一抽象                       │
│  - attributes/preferences/relations/states                │
└──────────────────────────────────────────────────────────┘
```

**核心价值**：
1. **短期记忆**用"段+密度"过滤噪音，保证注入的对话上下文高价值
2. **MemoryCompressor**保证长期记忆"少而精"，避免重复和过期信息堆积
3. **EntityProfile**让记忆系统能处理"多主体"场景（用户+项目+产品）

## 工程问题补充

### 4.1 合并冲突（生产环境需注意）

**问题**：当多条相似消息都触发 MERGE 时，可能产生合并冲突。

**示例**：
```
已有: "用户喜欢川菜和湘菜"
新来: "用户喜欢日料"
新来: "用户喜欢西餐"
→ 都和已有合并 → 长度爆炸
```

**解决方案**：
- 设置单条记忆最大长度（如 100 字符）
- 超长时再次触发 LLM 摘要
- 拆分为多条"原子记忆"

### 4.2 段边界检测的鲁棒性

**当前简化**：
- 单段 Token 超限 → 结束
- 5 分钟无消息 → 结束
- 手动结束

**生产环境增强**：
- LLM 识别话题切换
- 用户明确信号（"换个话题"）
- 时间窗口（兜底）

### 4.3 密度评分的准确性

**当前局限**：
- 规则匹配有遗漏
- 多义词可能误判
- 上下文相关性无法捕捉

**生产环境增强**：
- 用 LLM 做单条消息价值评分
- 结合实体识别（NER）
- 引入用户反馈（用户标注"重要/不重要"）

### 4.4 实体画像的关系图谱

**进阶方向**：
- 多个 EntityProfile 之间构建关系图谱
- 加载时按图谱扩散（用户→关联项目→关联产品）
- 支持"上下文图"注入
