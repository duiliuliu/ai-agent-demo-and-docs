# 03-memory 工程问题与设计文档

## 一、记忆加载时序设计

### 1.1 核心问题：什么时候加载什么记忆？

不是所有记忆都每次全量加载——那样 Token 消耗巨大且噪声多。应根据**对话上下文、意图、轮次**动态决策。

### 1.2 加载时序（Load Order）

```
请求到达
  │
  ├─ 1. 用户画像 (CACHED)
  │    新会话时加载 → 后续轮次缓存复用
  │    理由：体量小、价值高、变动少
  │
  ├─ 2. 长期记忆 (PARTIAL)
  │    取最近 N 条（非全量）
  │    理由：全量加载 Token 爆炸，最近的最相关
  │
  ├─ 3. 向量记忆 (ON_DEMAND)
  │    仅当用户输入有查询意图时触发搜索
  │    理由：向量搜索是 O(N) 的，无意图时浪费
  │
  └─ 4. 短期记忆 (FULL)
       每轮都全量加载（受 Token 限制保护）
       理由：当前对话上下文最关键，放最后（近因效应）
```

### 1.3 加载策略矩阵

| 记忆类型 | 策略 | 触发条件 | Token 占比 |
|---------|------|---------|-----------|
| 用户画像 | CACHED | 新会话加载，后续缓存 | 15% |
| 长期记忆 | PARTIAL | 条目 > N 时取最近 N 条；≤ N 时 FULL | 25% |
| 向量记忆 | ON_DEMAND | 检测到查询意图（疑问词/搜索词/首轮） | 10% |
| 短期记忆 | FULL | 每轮都加载 | 50% |
| 任意 | SKIP | 记忆为空或不满足触发条件 | 0% |

### 1.4 决策树

```
is_new_session?
├─ Yes → 加载用户画像到缓存
└─ No  → cache_valid? 
        ├─ Yes → 复用缓存（0 tokens）
        └─ No  → 重新加载

long_term.size > partial_limit?
├─ Yes → PARTIAL：取最近 N 条
├─ No  → 条目数 == 0? 
│       ├─ Yes → SKIP
│       └─ No  → FULL：全量加载
└─ 

has_query_intent(user_input)?
├─ Yes → ON_DEMAND：搜索 top-K 相关记忆
└─ No  → SKIP

short_term.size > 0?
├─ Yes → FULL：全量加载
└─ No  → SKIP（首轮对话）
```

### 1.5 为什么短期记忆放最后？

LLM 的注意力机制对 **Prompt 末尾的内容更敏感**（近因效应）。当前对话上下文是最关键的上下文信息，放在 Prompt 末尾能确保 LLM 优先关注。

## 二、Token 预算管理

### 2.1 问题：记忆注入会显著增加 Token 消耗

每次请求注入用户画像 + 长期记忆 + 向量记忆 + 短期记忆，可能消耗数千 Token，直接影响：
- **成本**：Token 越多，API 调用费用越高
- **延迟**：Prompt 越长，推理时间越长
- **质量**：过多记忆注入会分散 LLM 注意力，降低回答质量

### 2.2 Token 预算分配策略

```python
# 默认分配（总预算 4000 tokens）
ratios = {
    "short_term": 0.50,   # 2000 tokens - 当前对话最重要
    "long_term": 0.25,    # 1000 tokens - 历史事实
    "user_profile": 0.15, # 600 tokens  - 个性化基础
    "vector": 0.10,       # 400 tokens  - 语义相关
}
```

### 2.3 截断策略

| 记忆类型 | 截断方式 | 原因 |
|---------|---------|------|
| 用户画像 | 截断标签部分，保留基本信息 | 基本信息价值更高 |
| 长期记忆 | 从最旧开始删除 | 最近记忆更相关 |
| 向量记忆 | 按相似度排序，保留 top-K | 低分的噪声大 |
| 短期记忆 | 从最旧开始删除 | 最新对话最关键 |

### 2.4 Token 估算公式

```
estimated_tokens ≈ len(text) / 4
```
- 中文：约 1 字 ≈ 1-2 tokens（取保守值 2）
- 英文：约 4 字符 ≈ 1 token
- 混合：按 `len(text) / 4` 近似（偏保守）

## 三、分布式一致性问题

### 3.1 问题描述

多个 Agent 实例同时服务同一用户时，记忆的读写可能产生冲突：

```
实例A: 读取长期记忆 → 生成回复 → 写入新记忆
实例B: 同时读取长期记忆 → 生成回复 → 写入新记忆
结果: A 和 B 都基于旧记忆回复，B 的写入可能覆盖 A 的
```

### 3.2 解决方案

| 方案 | 适用场景 | 优缺点 |
|------|---------|--------|
| **乐观锁** | 冲突较少 | 读快写慢；冲突时需重试 |
| **版本号** | 写入频繁 | 需要维护版本号字段 |
| **写入队列** | 强一致 | 写入延迟增加 |
| **读写分离** | 读多写少 | 读快；写入最终一致 |

### 3.3 本 Demo 的简化处理

```
短期记忆：纯内存，无一致性问题（单实例）
长期记忆：文件存储，单机无冲突；多实例需换 Redis/DB
向量记忆：同上
用户画像：读多写少，适合缓存 + 失效策略
```

### 3.4 生产环境建议

1. **短期记忆** → Redis（TTL 自动过期）
2. **长期记忆** → PostgreSQL/MongoDB（事务保证）
3. **向量记忆** → Milvus/Chroma（专用向量数据库）
4. **用户画像** → Redis 缓存 + DB 持久化
5. **写入策略** → 异步写入 + 乐观锁

## 四、向量检索准确性问题

### 4.1 TF-IDF 的局限性

本 Demo 使用词频向量 + 余弦相似度，存在以下问题：

| 问题 | 示例 | 原因 |
|------|------|------|
| 无语义理解 | "天气" vs "气象" 不匹配 | 词频只看字面重叠 |
| 中文分词 | "北京天气" vs "北京的天气" | 本 Demo 用字符级分词 |
| 长文本稀释 | 长记忆和短查询相似度低 | 向量被更多维度稀释 |
| 多义词 | "苹果"（水果 vs 手机品牌） | 无法区分上下文 |

### 4.2 改进方向

```
当前 Demo          →    生产环境
─────────────────────────────────────
TF-IDF             →    Embedding 模型 (text-embedding-3-small)
字符级分词          →    专业分词器 (jieba/HanLP)
余弦相似度          →    余弦 + Rerank (cross-encoder)
线性扫描            →    ANN 索引 (FAISS/HNSW)
单语言              →    多语言 Embedding
```

### 4.3 混合检索策略

```
用户查询
  ├─ 关键词搜索（精确匹配）
  ├─ 向量搜索（语义匹配）
  └─ 合并 + Rerank → top-K 结果
```

### 4.4 Rerank 的价值

向量检索召回的 top-K 可能包含噪声。使用 cross-encoder 做二次排序：
1. 向量检索召回 top-20（宽召回）
2. Cross-encoder 对 20 条逐一打分（精排序）
3. 取 top-3 注入 Prompt

## 五、哪些记忆应当加载？如何加载？

### 5.1 加载决策矩阵

| 场景 | 用户画像 | 长期记忆 | 向量记忆 | 短期记忆 |
|------|---------|---------|---------|---------|
| 新会话首轮 | CACHED | PARTIAL | ON_DEMAND | SKIP(空) |
| 对话中轮 | 缓存 | PARTIAL | ON_DEMAND | FULL |
| 简短确认 | 缓存 | SKIP | SKIP | FULL |
| 新话题 | 缓存 | PARTIAL | ON_DEMAND | FULL |
| 会话结束 | 不加载 | 不加载 | 不加载 | 转换为长期 |

### 5.2 加载方式对比

| 方式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **全量(FULL)** | 短期记忆、小量长期 | 信息完整 | Token 消耗大 |
| **部分(PARTIAL)** | 大量长期记忆 | Token 可控 | 可能漏掉旧信息 |
| **按需(ON_DEMAND)** | 向量记忆 | 零开销(不触发时) | 需意图检测 |
| **缓存(CACHED)** | 用户画像 | 零重复开销 | 需失效策略 |
| **跳过(SKIP)** | 空记忆/不相关 | 零开销 | 无信息 |
| **增量(DELTA)** | 仅变化部分 | 最省 Token | 需维护版本 |

### 5.3 增量加载（进阶）

对于长期记忆，可以只加载自上次加载以来的变化：

```python
# 伪代码
last_loaded_version = session.get("ltm_version")
new_entries = long_term.get_since(last_loaded_version)
# 只注入 new_entries，旧的不重复加载
```

## 六、记忆更新覆盖问题

### 6.1 问题：记忆冲突时如何处理？

用户说"我喜欢川菜"，后来又说"我改吃粤菜了"——旧记忆需要被覆盖还是保留？

### 6.2 策略

| 策略 | 处理方式 | 适用场景 |
|------|---------|---------|
| **覆盖** | 删除旧的，写入新的 | 偏好变更 |
| **追加** | 保留旧的，追加新的 | 事实记录 |
| **版本化** | 保留历史版本，标记最新 | 审计需求 |
| **合并** | 用 LLM 合并新旧记忆 | 复杂信息 |

### 6.3 本 Demo 的实现

```python
# MemoryManager 提供更新接口
mm.update_long_term(index, new_content)  # 覆盖更新，同步向量索引
mm.delete_long_term(index)               # 删除记忆，同步向量索引
```

## 七、短期→长期记忆转换

### 7.1 为什么需要转换？

短期记忆有容量限制（max_entries / max_tokens），对话久了旧消息会被驱逐。需要将重要信息提取到长期记忆。

### 7.2 转换时机

```
短期记忆 Token 数 > min_tokens (如 200)
  → 触发转换
  → 将短期记忆写入长期记忆 + 向量索引
  → 清空短期记忆
```

### 7.3 生产环境改进

本 Demo 直接搬运短期记忆到长期。生产环境应：
1. 用 LLM 对短期记忆做**摘要压缩**（减少 Token）
2. 提取关键信息（偏好、事实、决策）写入长期
3. 保留原始对话到归档存储（不注入 Prompt）
